# JazGot Tours: focused presenter notes

Ten slides. Allow approximately 10–15 minutes, depending on pace and pauses. Detailed QA records remain in the full report and workbook.

## 1. Introduction

Good morning. This report covers the second QA iteration for JazGot Tours, a website for selecting tour packages, entering a booking, going through checkout and viewing an invoice. Our role was to verify whether the implemented customer journey behaved as expected. The central finding is that a customer can move through the screens, but the details shown afterward do not match the booking they entered. We also reproduced the invoice-download failure. Before interpreting those findings, one source point is worth establishing: the application code in the tested copy matches the official repository’s current main branch at commit fffd308. The copy adds testing tools and documents. I will cover the starting point, what was tested, the results and the fixes that need verification. Authentication and payment are simulated, so this report does not describe real charges or confirmed business transactions.

## 2. Iteration 1 baseline

The recorded first iteration executed eight customer-flow cases. Seven passed and one failed, which gave an 87.5 percent pass rate. The passing cases established that users could browse tours, open the authentication flow, complete simulated registration, calculate a booking total, proceed to checkout and view dashboard details. The failed case was invoice PDF export: clicking download produced no file. The key limitation in those earlier passes is the wording of the checks. They checked whether a page or information appeared, but did not consistently compare that information with what the customer entered. A dashboard can display a name and total and still display the wrong name and total. Iteration 2 therefore revisits the PDF defect and adds checks for data accuracy and invalid input. We should interpret the earlier results as evidence for those specific assertions, rather than evidence that every part of the booking feature worked.

## 3. Test scope

This round covered the main customer flow from selecting a tour through simulated checkout to the dashboard. It also checked whether guest counts, dates and amounts survived navigation, whether a PDF could be downloaded, and whether invalid inputs were rejected. Basic admin checks and a clean Windows dependency installation were included. The tests ran against a local production build using Playwright with Microsoft Edge, which uses Chromium. Screenshots, console logs and a browser trace were saved. The scope limits matter when we state the result. We did not verify real payment processing, database persistence, security, performance under load or accessibility conformance. We also did not run a browser matrix. Some requirements were inferred from the supplied deck and implemented interface because completed requirements were unavailable. I will identify the quotation record-creation case separately because that expectation still needs agreement.

## 4. Iteration 2 results

The corrected test set contains eighteen cases. Eight passed, nine failed and one was blocked. Seventeen cases therefore reached a pass-or-fail outcome, and eight divided by seventeen gives the reported pass rate of 47.06 percent. If the denominator includes all eighteen planned cases, the share passing is 44.44 percent. The blocked case is PDF content comparison: there was no downloaded PDF to inspect. The eight passes consist of the seven earlier navigation and display checks, plus the empty-payment-field check. A lower pass rate than Iteration 1 does not by itself show that development made the software worse. The second round asks additional questions that the first round missed. We are now checking whether the booking data is correct and whether invalid input is refused. The detailed workbook records each case; the following slides focus on the failures that explain the outcome.

## 5. Booking data mismatch

This example shows the main customer impact. The test selected Tour A at 1,350 pesos per person, enabled the 400-peso ETDF fee and 200-peso lagoon fee, and entered two guests. The booking form correctly calculated 3,900 pesos. It also accepted a future tour date, September 27. On checkout, however, the display changed to one guest, 1,350 pesos and a pending date. The dashboard repeated those values and used a sample customer name. These are observable mismatches, so the continuity tests failed; they were not blocked. The earlier payment-navigation test still passed because the application reached the next screen, but reaching that screen did not preserve the transaction. The practical impact is that the customer reviews a different booking from the one they requested. The recommended fix is to carry the actual booking state through checkout and the dashboard, then compare all relevant fields in a retest.

## 6. Invoice PDF failure

The invoice download was the defect carried over from Iteration 1. In the current live retest, clicking Download PDF Invoice still produced no file. The console reported an unsupported colour function named lab. The application uses html2canvas to turn the visible invoice into an image, then uses jsPDF to put that image into a PDF. The failure occurs in that export path. We do not need to choose the developer’s exact implementation to state the acceptance condition: a file must download, open, remain readable and contain the correct invoice details. BUG-001 stays open because that did not happen. The separate content-comparison test is blocked by this failure, since it requires an existing PDF. That explains the difference between the failed download test and the blocked content test. The detailed report includes the console evidence and possible repair approaches.

## 7. Input validation

We tested three negative cases. A negative test passes when the application correctly refuses invalid input. First, submitting an empty payment form was rejected by required-field validation, so that case passed. This corrects the original deck’s claim that the payment form had no validation at all. Second, malformed nonempty payment details were accepted. We separately tested an alphabetic card number, an impossible expiry entry and an alphabetic CVC while keeping the other fields in normal format. Each variant reached the simulated success dashboard. These variants belong to one test case, not three extra cases in the total. Third, a tour date ten days before execution was accepted and led to checkout. That case also failed. The development action is to keep the existing required-field checks and add meaningful rules for card details and booking dates. None of these outcomes represents a real payment being approved.

## 8. Admin and setup

Three other findings affect setup and the admin area. A clean Windows installation failed because the dependencies included a Linux-only Tailwind package. A forced installation allowed the rest of QA to proceed without editing the application, but the clean-install case remains failed. In the admin area, all five routes returned content. The quotation page nevertheless raised a React hydration runtime error. In plain terms, the initial server-rendered page and the browser’s version did not match. The page recovered visibly, so we should not describe it as a blank-page crash. Finally, the deck expected quotation submission to create a record, but the page provided a live preview with no submit or save action. That fails the written test case, while the requirement itself still needs scope agreement. It is recorded separately from confirmed defects against clear expectations. These distinctions keep the report fair to the developers.

## 9. Recommended next steps

The recommendations follow the observed failures. Preserve actual booking details through the customer flow, so the selected guest count, date, add-ons and price appear consistently. Resolve the invoice export error and verify the resulting file. Keep required-field validation while rejecting malformed payment values and past tour dates. Correct the platform-specific dependency so another tester can install the project cleanly on Windows. For admin, resolve the quotation runtime error and agree whether record creation belongs to this iteration. These are actions for the development team; the QA run did not alter the submitted application to make the tests pass. Once a fix is returned, QA should repeat the relevant failed case and check the surrounding behavior for regressions. The workbook provides steps, expected results, observed results and evidence, so each retest can target the specific issue instead of relying on a general statement that it was fixed.

## 10. Final assessment

The stated exit criteria are not met. The pass rate is below the 95 percent target, invoice export still fails, and high-severity booking-data and payment-validation issues remain open. All eighteen cases have an outcome or documented blocker, so the test report is complete even though the software has not met the acceptance conditions. The conclusion is that basic navigation works, but a successful-looking journey does not yet produce a reliable booking or downloadable invoice. The next step is focused development fixes followed by retesting, with the quotation record requirement clarified separately. The report and workbook contain the full case list and evidence for questions. Thank you.
